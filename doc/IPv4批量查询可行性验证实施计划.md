## 2. 实现方案与接口

### 数据加载与存储

- Rust 使用 Apache Arrow Rust/Parquet，Java 使用 Apache Parquet Java；复用现有解码能力，只读取两个边界列和八个业务列。Rust 的官方 reader 提供列投影和分批读取能力。[Arrow reader 文档](https://arrow.apache.org/rust/parquet/arrow/arrow_reader/struct.ArrowReaderBuilder.html)、[Parquet Java](https://github.com/apache/parquet-java)
- 加载时逐值检查 INT64 边界属于 IPv4 范围，转换为连续 `u32[]`／Java `int[]`；校验覆盖跨 batch、跨 Row Group 边界，任何违例整体加载失败。
- 载荷采用分块 UTF-8 数据、offsets 和 validity 表示；Java 保持同等布局，避免常驻数亿个 `String` 对象。首轮不增加自定义字典压缩。
- 数据版本使用文件 SHA-256 标识，并记录 schema、行数和投影字段。原始 dump 保持不变，不纳入源码 Git。

### 查询与返回契约

- 两个实现采用相同的连续起终点数组与前驱二分查找，校验候选终点；默认由调用线程执行，不启用 Rust 内部线程池。
- 提供共同的 Java 11 契约：`open(Path)`、`datasetVersion()`、带 offset/length 的 `lookupBatch(int[], …, long[], …)`、`fetchBatch(long[], …)` 和幂等 `close()`。
- `int` 按无符号 32 位 bit pattern 解释，负的 Java `int` 是合法输入。结果保持顺序和重复项；行号从 0 开始，`-1` 表示未命中，且只能交给产生它的同一快照解释。
- 固定返回 `country、province、scene、isp、owner、areacode、user、asnumber`。client/server 共用索引与字段映射，通过输出前缀区分；`areacode`、`asnumber` 保持原字符串值。
- `PayloadBatch` 提供命中状态、每列 validity、UTF-8 数据和 offsets，并提供转为 Java 字符串结果的适配方法。空字符串与 null 保持区别，关闭查询对象不影响已返回的 Java 数据。

### 输入过滤与 JNI 边界

- 保留独立的字符串便利入口，共用 Java 侧严格解析器：仅接受四段 ASCII 十进制、每段 0–255，除单独的 `0` 外不允许前导零；拒绝空白、端口、CIDR、IPv6、缩写及其他格式。
- 非法字符串保留原位置，返回 `INVALID_INPUT`；合法项区分 `MATCHED/NOT_FOUND`。整数热路径不执行字符串过滤；私网、环回、保留地址均按数据正常查询。
- JNI 使用区域复制读取输入、回写输出，不保留 Java 数组指针；采用受管理的句柄和调用期间引用，保证查询与关闭竞争时内存有效。错误转换为 Java 异常，panic 不跨 JNI 边界。[Java 11 JNI 规范](https://docs.oracle.com/en/java/javase/11/docs/specs/jni/functions.html)
- 首轮仅用显式绝对路径加载 `.so`，最大查询批次为 1,000,000；检查数组范围及容量计算溢出。

## 4. 验证与性能评估

### 正确性与生命周期

- 覆盖空数据、单点、端点、空洞、跨 `2^31`、`0`、`0xFFFFFFFF`、重复查询、offset、空批次、超限及错误数组参数。
- 真实 dump 全地址覆盖，因此真实数据上的合法 IPv4 命中率为 100%；0%、50%、90% 命中场景使用独立生成的带空洞数据。
- 小数据使用线性扫描 oracle；大合成数据使用可推导结果；真实数据使用区间边界样本、独立流式扫描校验和 Java/Rust/JNI 交叉比对。
- 检查八字段值、顺序、空字符串和 null；注入非法 schema、null 边界、越界及跨批次乱序，要求可靠拒绝。
- 覆盖并发查询、查询与关闭竞争、重复关闭和关闭后调用；执行小 fixture 100 次加载/释放、全量数据重复加载/释放及 30 分钟并发稳定性测试，分别观察存活分配与 RSS。

### Benchmark

- 数据集为真实全量 `N=32,307,681` 和文档约定的合成 `N=10,000,000`；每工作单元 `Q=1,000,000`，并发线程分摊总工作量。
- 主矩阵使用 `B=1,024/4,096/65,536`、`C=1/4/8`；补测 `B=1/256/1,000,000、C=1`，避免超大批次与高并发同时放大结果内存。
- 分别比较整数输入到行号、整数输入到八字段 UTF-8 结果、整数输入到八字段 Java 字符串三条路径；字符串解析入口另测。正式业务结论以包含结果消费的路径为依据。
- 使用相同输入、数据 hash、字段和消费方式；Java 与 JNI 放在独立进程交替测量，避免同时驻留两套全量快照。JMH 起始采用 3 forks、5×1 秒预热、10×1 秒测量。
- 报告吞吐、批次 P50/P95/P99、CPU、allocation/GC、稳态及峰值 RSS、加载时间；尾延迟样本不足时明确标注。当前 WSL2 结果仅作为本地可行性证据。
- 基础二分报告完成后，追加一次 Java/Rust 同等的 16 位前缀目录对照实验；排序双指针、DirectByteBuffer 和内部并行留待后续。

### 结论规则与默认边界

本轮不预设加速比或生产 SLO。报告按测量结果给出“继续 Native 产品化”“优先采用 Java”或“证据不足”的建议，并说明差异、误差及资源成本；功能通过与性能收益分别报告。当前没有真实查询轨迹，不将生成负载称为生产负载；任一正确性或生命周期问题未解决时，不给出可采用结论。
